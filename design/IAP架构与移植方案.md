# IAP Bootloader 架构解析与移植方案

| 项目 | 内容 |
|---|---|
| 版本 | V1.0 |
| 日期 | 2026-11-15 |
| 源工程 | `code/STM32F10x_IAP`（多机型 bootloader，从其他项目移植而来） |
| 移植目标 | ① 治具主板（GD32F103RCT6）② 被测主板（Dua_motor_pp_newstb2） |

## 1. 源工程架构解析

### 1.1 模块组成（删减后保留的文件）

| 文件 | 职责 |
|---|---|
| `src/main.c` | 启动判断（是否进入升级模式）、APP 有效性校验、跳转 APP、升级模式主循环 |
| `src/dis_update.c/.h` | **升级协议核心**：0x70 命令族处理、分包接收、CRC 校验、AES 解密、写 Flash |
| `src/aes.c` | AES-CBC 解密（固件包加密传输，密钥编译在代码里） |
| `src/flash.c / flash_port.c / flash_env.c` | Flash 擦写（含 EasyFlash 风格的 ENV 参数区） |
| `src/usartset_u1.c / usartset_u3.c` | 升级串口（DMA+IDLE 中断），通过宏统一别名 `*_bb` |
| `src/GD32_ADD.c/.h` | GD32 与 STM32 的时钟/串口差异适配 |
| `src/stm32f10x_bkp.c / stm32f10x_pwr.c` | 备份域/电源（PowerLock 用） |
| `inc/ymodem.h` | 地址宏（ApplicationAddress 等）；ymodem.c 已删，CRC 函数实际在 dis_update.c |

### 1.2 Flash 布局（现配置，64K/128K 机型）

```
0x8000000 ┌──────────────────┐
          │  Bootloader      │ 10KB（10 页×1KB）
0x8002800 ├──────────────────┤ ← ApplicationAddress / DIS_FWDATA_ADDR_START
          │  APP 代码区       │
0x8004800 │  APP 元数据块     │ ← APP_END_INDX_ADDRESS（固定在 APP 区偏移 0x2000）
          │   +0  APP末尾标记指针 │ 指向 APP 末尾的 0x145089bd
          │   +4  Program_Mark   │ 镜像内=0xFFFFFFFF；APP 写 0x55AA5A55 请求进 boot
          │   +8  Checksum       │
          │   +12 Checksumlen    │
          │   +16 Checksumdat    │
          │   +20 APP_SIGN       │ 机型签名（防串刷）
          │  APP 代码区（续）    │
          │  ...               │
 APP末尾  │  0x145089bd        │ ← APP_END_CHECK_VALUE
0x800F800/0x801C800 └──────────┘ （64K / 128K 上限）
```

### 1.3 启动判断逻辑（main.c）

满足以下**任一**条件即停留 boot 进入升级模式，否则跳转 APP：

1. `DFU_CheckUserApp()==0` —— APP 无效（末尾标记指针越界 / 末尾无 0x145089bd / Program_Mark 非 0xFFFFFFFF / APP_SIGN 不匹配）
   - **APP 请求升级的机制**：APP 收到 0x70 命令后把 Program_Mark 写成 0x55AA5A55 → 校验失败 → 复位后留在 boot。升级成功写入新镜像（该字恢复 0xFFFFFFFF）后自动跳 APP
2. `Hall_ReadState()==0x07` —— 三路霍尔线全高（工装/底座检测），进入升级等待（限时 HALL_MAX_WAITCNT）
3. CPU 类型不匹配（`checkcputypefit`，当前代码中被强制跳过 `cputypechedkflgrev=1`）

升级模式主循环：每约 40ms 主动发 `0x70/0x4C`（请求对方切协议/重置）帧；收到数据走 `USART_USER_IRQ_BBAPP` 分发：0x70→升级协议处理，0x9B→回机型版本。

### 1.4 跳转 APP

校验 APP 栈顶合法（`& 0x2FFE0000 == 0x20000000`）→ 关串口/定时器 → 开 IWDG（约 1.8s）→ 设 MSP → 跳转。**APP 工程必须配合：向量表偏移 0x2800**（治具框架 `app_main.c` 中已有 `NVIC_SetVectorTable(FLASH, 0x2800)`，DEV_DEBUG 模式下为 0——发布编译需关闭 DEV_DEBUG）。

## 2. 升级数据协议（0x70 命令族）

### 2.1 帧格式

- **命令/应答帧（20 字节）**：

```
[0]=0xAA [1]=0x55 [2..15]=数据 [16]=0x70 [17]=子命令 [18..19]=CRC16
```

  CRC16 = CRC16-CCITT（多项式 0x1021，初值 0），覆盖字节 [2..17]，**大端**存放（[18]=高字节）

- **固件数据帧**：20 字节头 + N×16 字节加密载荷（N≤27，单帧最大 20+432 字节）

### 2.2 升级流程（发送方 ↔ Boot）

| 步 | 方向 | 子命令[17] | 数据区 | 说明 |
|---|---|---|---|---|
| 1 | → | 0x10 或 0x40 | 0x40 时：[2..3]=整包CRC16，[14..15]=总包数(16B/包) | 发起升级；Boot 收到 0x40 后擦除 APP 区、初始化 AES |
| 2 | ← | 0x40 | — | 拒绝/请求重置（固件过大等） |
| 2 | ← | 0x41 | [2]=进度%，[14..15]=期望包序号 | 接受，请求第 0 包 |
| 3 | → | 0x41 | [2..3]=本包CRC16，[4..5]=包长(16B单位)，[14..15]=包序号，[20..]=加密载荷 | 发数据包；CRC 对**密文**计算 |
| 4 | ← | 0x41 | [2]=进度%，[14..15]=下一期望包序号 | 校验通过、写 Flash 后请求下一包 |
| … | | | | 循环 3-4 直到全部包收完 |
| 5 | ← | 0x42 | 成功：[2]=100,[6]=1；失败：[2]=0 | 主循环整包 CRC 核验 + APP 有效性复检后的结论 |
| 6 | — | — | — | 校验通过则延时后跳转 APP |

关键细节：
- 整包 CRC 与分包 CRC 均对 **AES 密文** 计算（Boot 先验 CRC 再解密写入）
- AES-CBC：16 字节分组，链块初始为全 0，密钥编译在 aes.c 中——**打包工具必须用同一密钥加密**
- 包序号必须严格递进，断包由"请求期望序号"机制恢复（重发指定包）
- Boot 空闲时周期发 `0x70/0x4C`，发送方可用它发现 Boot 在线

### 2.3 配套工具链

- `bin2bt.exe`（在治具 app 工程 project/ 目录）：把 APP 的 bin 转成加密升级包（如 `KS_N10.bin`），并写入末尾标记/签名区——**两个 APP 工程的编译后脚本都要调用它**
- Boot 应答 `0x9B`：回机型码+boot 版本（`BootSoftVersion` 字符串定位在 0x8001300）

## 3. 移植方案

### 3.1 共性工作（两个目标都要做）

| 项 | 内容 |
|---|---|
| 清理残留依赖 | `usartset_u1.c/u3.c`、`main.c` 仍 `#include "bbcpro.h"`（已删除）——移植时移除；`crcinpack` 只在非 FX1 分支用（显示板包壳协议），**两个目标都用不到，相关 `#else` 分支直接删除** |
| 新增机型宏 | 建议 `MODEM_KS_JIG`（治具）、`MODEM_KS_ZZDW`（被测主板），GPIO/签名/通道选择全部挂到各自宏下 |
| APP_SIGN | 两个目标各定义一个**互不相同**的签名值（如治具 0x14500301、主板 0x14500302），防止固件互刷 |
| AES 密钥 | 确认沿用现有 aes.c 密钥还是换钥；换钥则 bin2bt 端同步 |
| Flash 页大小 | GD32F103RCT6 页 2KB（大容量），擦除函数按页对齐处理 |

### 3.2 治具主板（GD32F103RCT6，256KB Flash）

| 项 | 方案 |
|---|---|
| 升级通道 | **备用串口 U11（UART4，PC10/PC11）**——把 app 工程的 `usartset_u4.c` 移植进 boot 并别名 `_bb`；升级源为电脑端上位机 |
| 进入升级 | ① APP 请求（Program_Mark 机制，协议 0x70 触发，APP 侧加 `iapgoboot()`）；② **上电时按住 KEY3**（治具无霍尔线，用面板按键替代 Hall 检测，新增按键检测代码） |
| GPIO 配置 | 蜂鸣器 PA8（提示音）、运行灯 PA10（升级中快闪）；删除 PowerLock/Hall 相关 |
| 地址规划 | Boot 0x8000000 起 10KB 不变；APP 0x8002800；上限放宽到 256K（`LARG_FLASH_IC_USED` 分支按 0x803F800 调整）；元数据块 0x8004800 不变 |
| 价值 | 治具固件可远程升级，产线不用拆机 |

### 3.3 被测主板（Dua_motor_pp_newstb2）

| 项 | 方案 |
|---|---|
| 升级通道 | **UART4（PC10/PC11，115200）**——与 APP 协议/治具对接同一物理口，治具经 CN8 即可给主板升级；移植 app 工程的 `usartset_u4.c` 别名 `_bb` |
| 进入升级 | ① APP 请求：APP 已有 `iapgoboot()`（appfun.c case 0x70），只需确认 Program_Mark 地址与 boot 一致；② 霍尔全高检测（保留，产线工装可用）；③ 治具通过 JIG_PROTO 扩展子命令触发 |
| 机型配置 | 新增 `MODEM_KS_ZZDW`：GPIO 段按主板实际（蜂鸣器/Hall 引脚从主板原理图取）；APP_SIGN 用新值 |
| GD32 适配 | 主板也是 GD32，GD32_ADD.c 直接复用 |
| 与 selfcheck 的协同 | 治具测试流程中可加一步"固件版本不符 → 先升级再测试"，实现烧录测试一体化 |

### 3.4 治具兼任"升级发送方"（推荐，可选二期）

Boot 协议是主从式，**治具可以实现发送方逻辑**：经备用串口从电脑接收主板固件包 → 经 CN8/UART4 按 §2 协议发给被测板 Boot。这样产线换固件不用烧录器，治具屏上直接显示升级进度（协议里自带进度百分比）。

## 4. 移植实施顺序建议

1. **先治具**：新增 MODEM_KS_JIG 配置，砍掉显示板包壳/霍尔/PowerLock，UART4 通道，按键进入升级——代码量小、可独立验证（电脑端发包测试）
2. **再主板**：新增 MODEM_KS_ZZDW，UART4 通道，与 APP 的 0x70 跳转联调
3. **打包工具验证**：用 bin2bt.exe 分别打包两个 APP，确认标记区、签名、加密一致（先在开发板上全流程跑通一次再投产）
4. 二期：治具桥接升级被测板
